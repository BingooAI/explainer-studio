# Explainer Studio — Architecture

> **Status: v0.1 — living document.** Nothing in `packages/` or `apps/` exists yet, so parts
> of this are reasoned rather than proven. It is the map [`ENGINEERING.md`](ENGINEERING.md)
> enforces; changing it needs an ADR in `docs/adr/`. Scheduled review: end of Phase 1, when
> there is real code to argue back.
>
> **For who this is built and what comes out of it, see [`PRODUCT.md`](PRODUCT.md).**

Explainer Studio turns a lesson brief into an editable explainer video: script, visuals,
narration and timeline, generated by a model, then edited scene by scene and exported.
It is self-hostable, model-agnostic, runs fully on localhost, and is Apache-2.0 throughout.

Prior art: the `explainer` subsystem inside Bingoo's private monorepo. This project is a
clean-room restructuring of that design, not a copy — the parts that only make sense inside
Bingoo are removed, and the places where that implementation is static or hardcoded are
rebuilt as runtime registries (§2, §11).

---

## 1. The load-bearing idea

Everything follows from one function:

```ts
frame(program: Program, t: number): RenderModel
```

**Pure. Same `t` ⇒ same `RenderModel` ⇒ identical pixels on any renderer.**

The engine decides *what is on screen at time t*. A renderer is a dumb painter of
`RenderModel` — it owns no timing, no layout, no animation curves. That is why a React/SVG
renderer, a React Native renderer and a headless export renderer can never drift apart, and
why the whole engine is testable without a browser.

Two consequences we design around from the first commit:

- **Authors declare intent, never milliseconds.** A scene says `reveal`, `emphasize`,
  `drawOn`. Easing and duration live in a timing profile, not in the scene.
- **Structure and language are separate.** `ExplainerDoc` is language-neutral. Every string
  a human reads lives in a `LocaleBundle`. One doc, N languages, one timeline.

## 2. Dynamic by default — the anti-hardcoding rule

**Nothing that a user, deployer or contributor might reasonably want to change may be a
literal in code.** No vendor switch statements, no baked-in model lists, no hardcoded
catalogs, no rebuild to add a provider, a template, a voice or a language. If extending the
product requires editing a `case` branch, the design is wrong.

This is the rule the rest of the architecture serves, so it is stated before the layers.

### 2.1 Everything extensible is a registry

Each of these is a **runtime registry** — a map populated at startup from descriptors, open
for registration by plugins, and queryable by the UI:

| Registry | Contains | Extend by |
|---|---|---|
| Providers | LLM · voice · image · search · storage · moderation | dropping in a provider manifest |
| Layout templates | teaching-move templates + slot definitions | adding a template descriptor |
| Motion grammar | emphasis keyframes, transitions, timing profiles | adding a profile |
| Themes | token sets, light/dark, brand packs | adding a theme pack |
| Locale packs | strings, speech-rate + glyph-metric tables, contract prose | adding a locale pack |
| Question kinds | gate item schemas + graders | registering a schema + grader |
| Interactive kits | manipulatives, diagrams | registering a kit |
| Exporters | MP4, VTT, SCORM, xAPI, … | registering an exporter |
| SFX / assets | sound and asset catalogs | catalog file |

A registry entry is **data plus a factory**, validated by zod on registration. An invalid
descriptor fails loudly at startup, never silently at render.

### 2.2 Providers are configured, not compiled

A provider is declared, not imported by the core:

```yaml
# explainer.config.yaml — resolved at runtime
providers:
  llm:
    - id: local
      kind: openai-compatible          # adapter id from the registry
      baseUrl: http://localhost:11434/v1
      model: ${LLM_MODEL:-qwen2.5:14b}
    - id: cloud
      kind: anthropic
      apiKey: ${ANTHROPIC_API_KEY}
  voice:
    - id: local
      kind: piper
      voice: ${PIPER_VOICE}
routing:
  llm:   [local, cloud]                # ordered: failover, not a hardcoded pair
  voice: [local]
```

Rules:

- **Model IDs are never literals in code.** They come from config, and where a provider can
  enumerate its own models (`/v1/models`, Ollama's tag list), the UI lists them live.
- **Capabilities are declared, not assumed.** Each adapter publishes a descriptor —
  modalities, context window, streaming, word-level timings, cost hints. Features light up
  from the descriptor. Code never asks *"is this OpenAI?"*; it asks *"does this support
  word timings?"*
- **Routing and failover are config**, an ordered list, not an `if` chain.
- **Adding a provider touches no existing file** — a new adapter module plus a manifest.
  This is the acceptance test for the whole design.
- Secrets resolve through env interpolation and stay server-side; config is safe to commit,
  `.env` never is.

### 2.3 Constants become profiles

The engine still needs timing and layout numbers — but they live in a **named, versioned
profile** loaded as data, with the built-in set as the default:

```
timing profile:   reveal · stagger · draw · move · easing curves
type scale:       rungs, char budgets
layout budgets:   fill ratio, overlap threshold, canvas sizes per aspect
speech metrics:   words-per-second and glyph width, per script
```

Documents pin a profile version, so a lesson authored today renders identically after we
tune the defaults. Tuning "how the house animates" is editing a profile, never editing
`choreographer.ts`.

### 2.4 Configuration is layered and reloadable

Precedence, lowest to highest: **built-in defaults → config file → environment →
workspace/project settings → runtime UI settings**. One resolver, one validated shape,
one place to read it. Changing a setting must not require a rebuild, and where it is safe,
not a restart either.

### 2.5 No hotfix culture

A bug is fixed at the layer that owns it, with a regression test, behind the same gates as
any other change. No special-case branch for one lesson, one tenant, one model. If
something needs to differ per deployment, that is a config surface — design it as one.

## 3. Stack and repository shape

Chosen for one criterion above all: **a contributor should be able to run and understand
this without asking us anything.** Boring, widely-known tooling beats clever tooling in a
project whose success depends on outside contribution.

| Layer | Choice | Why this and not the alternative |
| --- | --- | --- |
| Language | **TypeScript strict** | Zod gives us runtime validation and types from one source; that pairing is the backbone of §5. |
| Monorepo | **pnpm workspaces + Turborepo** | What the team already runs. Strict `node_modules` catches undeclared deps, which is exactly the discipline the purity rule (R7) needs. |
| Validation | **Zod** | Single source of truth for schema *and* type. Non-negotiable — the whole gate design rests on it. |
| Package build | **tsup** (esbuild) → ESM + CJS + `.d.ts` | Fast, config-light. Fixes the Bingoo defect where packages only compiled inside the repo (§14.2). |
| Tests | **Vitest** | Same transform as the build; golden fixtures for pure packages. |
| Renderer | **React 19 + SVG** | SVG keeps text selectable and accessible (WCAG, §15), is inspectable, and serialises for headless export. Canvas would cost us all three. |
| App | **Next.js (App Router)** | Self-hostable as a plain Node server. No platform-specific features — nothing may assume Vercel. |
| API | **Hono** | Small, standards-based, runs on Node/Bun/edge. Keeps the server a thin adapter layer. |
| DB | **SQLite by default, Postgres optional** — via **Prisma** | SQLite is what makes R9 true: no service to install. One schema, both engines. |
| Video export | **ffmpeg** | See §17.3. Apache-2.0-compatible story, no per-seat licence. |
| Local model path | **Ollama + Piper** | Keyless, offline, no account. The default that makes "self-hostable" real. |
| Lint/format | **ESLint type-aware + Prettier** | Type-aware rules are what mechanically enforce R7 purity in CI. |
| Release | **changesets** + Conventional Commits | Standard, and it handles a multi-package repo honestly. |

**Deliberately not chosen:** Remotion (licence, §17.3), Tailwind in the *renderer* (the
Stage paints from `RenderModel`, so styling is data, not classes — Tailwind is fine in the
studio chrome), a bundler-per-package, and any hosted service as a hard dependency.

Apache-2.0 for every path.

```
packages/
  core        @bingoo.ai/explainer-core        pure engine + doc schema + profiles
  quality     @bingoo.ai/explainer-quality     lint · layout gate · pedagogy gate · prompt contract
  providers   @bingoo.ai/explainer-providers   port interfaces + registry + vendor-neutral helpers
  generator   @bingoo.ai/explainer-generator   outline → write → critic → regen
  react       @bingoo.ai/explainer-react       SVG renderer + player
  editor      @bingoo.ai/explainer-editor      scene editor: op layer + panels
  kits        @bingoo.ai/explainer-kits        first-party primitives, manipulatives, packs
  adapters    @bingoo.ai/explainer-adapters    LLM/TTS/image/storage implementations
apps/
  studio      Next.js — the self-hostable product
  server      Hono API — persistence, media, provider wiring
  cli         init · generate · validate · render · export
docs/
  adr/        architecture decision records
  spec/       document format spec (explainer/v1)
```

**Purity rule:** `core`, `quality`, `providers`, `generator` must not import `react`,
`next/*`, `react-native`, or Node builtins (`node:*`, `fs`, `path`, `crypto`). No `fetch`,
no `process.env`, no `Date.now()`, no `Math.random()`. Enforced by ESLint in CI.

Everything non-deterministic or vendor-specific enters through a port.

## 4. `core` — the engine

Zod is the single source of truth; every TS type is `z.infer<>`, so the runtime validator
and the compile-time types cannot drift.

### Document model (`explainer/v1`)

| Type | Holds |
|---|---|
| `ExplainerDoc` | `meta` · `locales[]` · `theme` · `profiles` (pinned versions) · `scenes[]` · `background` · `music` |
| `Scene` | `id` · `kind: exposition \| gate` · `layout` · `elements[]` · `beats[]` · `narrations[]` · `gate` · `transition` · `phase` |
| `Element` | `id` · `type` · `region` (a layout slot, never x/y) · `place` · `flow` · `content` · `style` · `poses` |
| `Beat` | `cue` (matches a TTS mark) · `actions: VisualAction[]` · `hold` |
| `VisualAction` | discriminated on `verb`: `reveal · drawOn · emphasize · move · exit · point · sfx · connect · highlightPath · revealItem` |
| `Pose` | a *named discrete state* (`visible, x, y, scale, opacity, rot, emphasis, drawProgress`); `"base"` is rest |
| `LayoutSpec` | `template` — a **teaching move** resolved from the template registry — plus `regions` and per-aspect overrides |
| `GateSpec` | `kind` (from the question-kind registry) · `prompt` · `answer` · `feedback` |
| `LocaleBundle` | `locale` · `strings: Record<elementId, string>` · `narration: Record<id, Narration>` |
| `Narration` | `script` (with `[[cue:c1]]` markers) · `voice` · `audioUrl` · `marks: {cue,t}[]` · `words: {word,start,end}[]` |

**Elements never carry coordinates.** They name a `region`; `resolveLayout` computes rects
for each aspect ratio. Coordinates are *unrepresentable* in the authoring schema — a model
cannot produce an overlapping layout because it is never given the vocabulary to try.

Note that `template`, `gate.kind`, `element.type` and `emphasis` are **registry keys, not
enums frozen in the schema**. The schema validates that the key resolves; the registry
decides what exists. That is what lets a plugin add a template without a core release.

### Modules

- `schema.ts` — zod document model, `parseDoc` / `parseBundle`.
- `layout.ts` — `resolveLayout(scene, aspect)`, driven by the template registry and layout
  profile. Headless, so it doubles as the overflow linter.
- `choreographer.ts` — `compileScene → SceneTimeline{ duration, poseAt(id,t), … }`, reading
  the timing profile and motion grammar.
- `runtime.ts` — `buildProgram(doc, bundle, aspect) → Program`. Lays scenes end to end,
  marks gate pause points, derives duration from narration timings (or from the locale's
  speech-rate table before TTS has run).
- `frame.ts` — `frame(program, t) → RenderModel`. Resolves content; **derives chart geometry
  here** so a model can never hand us bars that contradict its own numbers.
- `type.ts` — the type scale and `charBudget(rect, rung)`. Lives in the engine, not the
  renderer, because "keep it short" must resolve to the same number the renderer will use.

## 5. `quality` — trust comes from code, not from the model

Three independent gates, all pure and deterministic. **No gate may call an LLM.**

1. `lintDoc(doc, bundles)` — schema validity, cue↔mark integrity, cross-aspect overflow,
   content-rect collision.
2. `checkScene(scene, strings, locale)` — measured against *the same* `resolveLayout` the
   renderer uses. Every finding carries a mechanical `fix` string, so repair is deterministic
   rather than a vague retry.
3. `checkLesson(doc, bundle)` — pedagogy as a contract: the phase arc
   `explore → orient → teach → formalize → guided → practice → recap → checkout`, each with a
   minimum scene count, plus a richness check that fails skeleton scenes.
   **The arc itself is a registry entry** — a curriculum with a different pedagogy registers
   its own arc rather than patching ours.

`prompt.ts` **generates the authoring contract from the live registries** — template
catalog, budgets, verb list, question kinds and reference lesson are emitted from the same
data the gates enforce. The prompt therefore cannot describe a rule the checker does not
implement, and a newly registered template is documented to the model automatically.
Generated artifacts land in `contract/` and are verified in CI.

This is the property worth protecting above all others: **a weaker model produces a worse
lesson, never an invalid one.** Quality degrades; validity does not.

## 6. `providers` — ports and the registry

Interfaces plus the registry. Zero vendor names, zero I/O.

```
LlmProvider · VoiceProvider · ImageProvider · MediaSearchProvider
TranslationProvider · SfxProvider · ModerationProvider · MediaStore
```

Every provider implements `descriptor()` (id, kind, capabilities, models) and
`available()`. The registry resolves config → adapters → an ordered routing chain, and
exposes what is actually available so the UI can render the real state of a deployment
rather than a guess.

Two pieces of vendor-neutral orchestration live here because they are pure logic:

- `cue.ts` — the sync spine. `cueMarksFrom(script, words)` re-times each `[[cue:x]]` marker
  to the start of the word that follows it; `evenWords()` is the offline fallback that uses
  the locale's speech-rate table.
- `resolveImage.ts` — illustration-first: search the library, accept a hit above the
  configured score threshold, generate only if nothing matches. Generation is the expensive
  path, so it is the last resort and always explicit.

## 7. `generator` — the pipeline

```
① OUTLINE  →  ② WRITE  →  ③ MODERATE (optional)  →  ④ CRITIC  →  ⑤ REGEN (weak scenes only)
```

- **① OUTLINE** (best-effort). Scene count comes from the *same* planner the arc gate uses,
  so the outline can never request fewer scenes than the gate demands. Failure → continue.
- **② WRITE** (required, bounded attempts). Each attempt passes through zod → lint →
  layout gate → arc gate, and **each failure is fed back as its mechanical repair
  instruction**, not as "try again".
- **③ MODERATE** (**optional, off by default**, pluggable). When enabled, narration,
  on-screen strings and gate prompts pass a `ModerationProvider` before anything is
  persisted or shown. Verdicts are per-span `allow | flag | block`: `block` is fed back to
  WRITE as a repair instruction like any other gate failure, `flag` is stored and surfaced
  in the editor for the author to judge.

  **The seam is mandatory even though the stage is not.** The wiring, the port, the verdict
  schema and the editor surface ship in Phase 3 whether or not a deployment turns it on —
  retrofitting this later would mean touching the pipeline, the persistence shape and the
  UI at once. Turning it on is config; adding it later is a migration.

  A deployment that enables it registers its own adapter (Azure Content Safety, OpenAI
  moderation, a local classifier, a district word-list). We ship a local keyless rule-based
  adapter as the reference implementation — it catches coarse problems, not nuance, and we
  say so rather than implying more.
- **④ CRITIC** (best-effort). An engine-aware judge scores each scene against sync,
  teaching, gates, pacing and visual richness — reading a compact digest, not raw JSON.
- **⑤ REGEN** (best-effort, guarded). Rewrites only scenes at or below the configured
  threshold, splices by id. **Guard: if gate errors increase, the rewrite is discarded.**
  A "fix" that makes a scene static is worse than the note.

Stage set, thresholds and attempt counts are configuration. Every stage except WRITE is
optional or best-effort, so output is never worse than a validated single-shot. The
pipeline is pure — the LLM arrives as a `LlmProvider`.

**Consequence to state plainly:** with MODERATE off — the default — generated narration is
validated for *structure* only. Nothing reads what the words say. That is a deliberate
choice (it keeps the localhost path keyless and the default install honest about doing no
content filtering), but it means the product must never be described as producing
moderated or classroom-safe text out of the box. See the claim-discipline rule in
[`ENGINEERING.md`](ENGINEERING.md) §6.

### Input: `LessonBrief`

```
version · topic · locales[] · audience{stage, grade} · subject{domain}
objectives[{statement, level, assess}] · source{materials[], grounding: open|strict}
facts[] · assets[] · misconceptions[] · priorKnowledge[] · constraints{sceneCount, imagePolicy, register}
```

`parseBrief` returns structured issues, never throws. Under `grounding: 'strict'` the
generator may only assert what the brief's `facts[]` contain.

**The studio does not decide pedagogy.** It receives objectives and verified facts; it
decides staging, visuals and timing. This is the boundary that keeps the project honest
about what it does and does not know.

## 8. Agents, reasoning and the autonomy boundary

The pipeline in §7 **is already an agent loop**, and deliberately a bounded one: WRITE
proposes, deterministic gates judge, failures return as mechanical repair instructions, it
retries. That shape is the asset. So it is worth being explicit about when more autonomy is
allowed and when it is not, before someone reaches for a framework.

### The rule

**An agent may loop only where a deterministic verifier closes the loop.** The gates (§5)
are the reward signal, and they are code — so the loop converges on something checkable
rather than on the model's own opinion of its work. The corollary is R2 restated:
**an agent is never the verifier.**

Everything else follows from that:

- **Every loop is hard-bounded** — max iterations, token budget, wall-clock, cost ceiling.
  A teacher pays per run (§12), so unbounded autonomy is a billing incident waiting to
  happen, not a capability.
- **Every loop records its trace as provenance** — prompts, verdicts, iteration count — so a
  run stays auditable and re-runnable (§11).
- **No agent has side effects.** Agents propose documents; only the pipeline persists, and
  only after the gates pass. No agent writes to storage, spends money outside its budget, or
  contacts anyone.
- **Tools are whitelisted per stage**, and every tool result re-enters as untrusted input.

### Reasoning is a provider capability, not a layer

Extended thinking is declared in the adapter descriptor (§2.2) and used when present. It
must never become a requirement. A local 14B with no thinking mode must still produce a
**valid** lesson — a worse one, but never an invalid one (§5). Never write a stage that only
works on a frontier model, or the model-agnostic claim in R8 is decoration.

### The gap this exposes: who writes the brief?

This matters more than the agent question itself, and it comes straight from the Bingoo
inheritance. §7's `LessonBrief` assumes objectives, verified facts and misconceptions
arrive **from upstream** — in Bingoo that upstream is the competency graph plus a human
authoring workflow. **In a standalone product there is no upstream.** A teacher types
*"teach photosynthesis to grade 7"* and drops in a chapter PDF.

So this product needs a stage Bingoo never had — **brief building** — and it is the one
place open-ended enough to genuinely warrant an agent:

```
teacher's ask + uploaded material
   → [brief agent: read · extract · ground · propose]
   → LessonBrief
   → ★ TEACHER APPROVES ★
   → §7 pipeline
```

- It reads the material, proposes objectives, misconceptions and facts, and keeps a
  `sourceRef` (file + page) for every claim, so each fact is traceable back to where it came
  from.
- Under `grounding: 'strict'` it may only propose what the material actually supports.
- **The teacher approves the brief before a single scene is generated.** This is the
  human-in-the-loop point of the entire product: a wrong objective is trivial to fix here,
  and expensive to fix after twenty scenes, narration and images have been paid for and
  rendered.
- Uploaded material is untrusted input — **prompt injection through a PDF a teacher
  downloaded is a real path**, not a theoretical one.

Approving the brief is also the honest division of labour, and it keeps §7's rule intact:
**the teacher owns what is taught; the studio owns how it is staged.** We propose; they
decide.

### What we are not building

- No autonomous swarm writing lessons unattended. Nothing verifies *pedagogy* except a
  person — the gates only check structure, and pretending otherwise is the overclaim `ENGINEERING.md` §6
  warns about.
- No agent that edits or republishes an existing lesson on its own.
- **No agent-framework dependency.** Ports, bounded loops and zod are the entire mechanism.
  Adding a framework here would import someone else's control flow into the one place we
  most need to reason about cost, determinism and failure.

## 9. Renderer and editor

`react` paints `RenderModel` into a single `<svg viewBox="0 0 w h">` in four layers:
backdrop → slot cards → items → chrome. SVG, not canvas: text stays selectable and
accessible, elements are inspectable, and the same tree serializes for export.

Element renderers come from a **component registry keyed by content type**, so a plugin that
registers a new element type ships its painter with it — the Stage never grows a switch.

**Audio is the master clock while speaking.** The playhead reads
`sceneStart + segment.at + audio.currentTime` during a narration line, so caption highlight
and visuals track the voice with no rAF drift, and falls back to rAF between lines. A
browser SpeechSynthesis fallback means every lesson has a voice with **no API key** —
which is also what makes the localhost demo work with nothing installed.

`editor` is scene-centric — you edit one scene at a time, like slides, with a derived clip
timeline underneath.

- **Every mutation is a pure `EditOp` with `apply(state, op) → {state, inverse}`.** Nothing
  mutates in place. The inverse is the backbone of undo/redo, version history and audit.
- The clip model is **derived from the cue/beat document** — the timeline never invents
  timing, so dragging a clip is translated back into `EditOp`s on beats and cues.
- The author never sees cue strings, verbs or canvas fractions. They see clips, effects and
  properties.
- Property panels are **generated from the registered schema** of the selected element, so a
  plugin's element is editable without touching the editor.

## 10. Kits, primitives and content packs — the contribution surface

This is where outside contributors will actually work, so it gets a first-class design
rather than an escape hatch. Three tiers, all registries (§2).

**Primitives** — atomic things the renderer can paint: `stroke · text · shape · image ·
connector · list · table · chart · stat · quote`. A primitive is a zod content schema + a
painter + its character-budget behaviour. Core ships the base set; a plugin may add one.

**Kits (manipulatives)** — an interactive unit that holds state: number line, fraction bar,
place-value blocks, balance scale. Used two ways, and this is the point of the design:
as a **scene element** the choreographer animates through verbs, and as a **gate** the
learner manipulates, graded by the kit's own pure `check`.

**Content packs** — a distributable bundle for a subject or level: templates, theme, locale
strings, example lessons, and the kits they depend on. This is how a publisher or a ministry
ships their material **without needing us** — the same property R8 protects for providers,
applied to content.

### Kits ship no binary assets

**A kit draws itself from primitives. It never bundles an image, icon, font or sound.**

This began as a licensing decision — bundled assets are where third-party terms (CC BY
attribution, non-commercial clauses) hide, and they are routinely missed because reviewers
read code and skim binaries. It survives as an architectural rule because it is simply
better:

- Manipulatives are geometric by nature — a number line, a fraction bar, a balance scale are
  *drawn*, not illustrated. Anything genuinely needing a picture asks the image provider
  (§6) at authoring time and stores a media *reference* (§11), which is where imagery
  belongs anyway.
- Sound comes from the `SfxProvider` or the deployment's own catalogue, never the kit.
- A kit stays small, diffable and reviewable — which matters when the whole point is
  outside contribution.
- Nothing can silently break the localhost guarantee (R9): a kit that needed a generated
  image to render at all would fail with no API key. **Kits must render with no provider
  configured.** Imagery is an enhancement, never a dependency.

Consequence for the picker: the thumbnail is **rendered from `examples.json`**, not shipped
as a file. One less asset, and a preview that cannot drift from what the kit actually does.

### Anatomy of a kit

```
kits/fraction-bar/
  kit.json        manifest — id, version, title, license, author, tags, verbs, requires
  schema.ts       zod: params + state
  kit.ts          defaults · verbs · transitions · pure check(state, answer)
  paint.tsx       painter, registered against the react renderer
  examples.json   golden fixtures · test corpus · picker preview data
  README.md
```

Rules, each with a reason:

- **Pure / painter split mirrors core / react.** Everything except `paint.tsx` must satisfy
  the purity rule (§3), so a kit works headless in MP4 export and in golden tests, not only
  in a browser.
- **Grading is code, never a model** (§5). A kit's `check` is pure and deterministic.
- **The manifest carries its own SPDX licence.** A contributed kit may be licensed
  differently from the repo, and we must be able to state that per kit. **A kit with no
  licence field is rejected at registration.**
- **No bundled assets** — enforced by `kit:validate`, which rejects any binary in a kit
  directory. A rule that is only written down is a rule that erodes.
- **Verbs are declared in the manifest** and flow automatically into the generated authoring
  contract (§5). A kit registered today is usable by the model today, with no prompt edit.
- **`examples.json` is mandatory.** It is the golden-test corpus *and* the preview data for
  the picker. A kit with no examples cannot be registered — untested kits are how a
  contribution surface rots.
- **Kits are versioned and documents pin the version**, so improving a kit never silently
  changes a lesson authored last term.

### First-party set — port Bingoo's 67, in waves

Bingoo's kit library is owned by the same company, so it is relicensed to Apache-2.0 and
brought here wholesale. The expensive part — the pedagogical and interaction design of 67
manipulatives — is already done and proven in classrooms. That is not worth rebuilding to
satisfy a boundary that does not actually exist.

Porting is still real work, though: per kit it means a manifest, a mandatory
`examples.json`, stripping hardcoded Vietnamese, decoupling from Bingoo's quiz types, an
SPDX header, and removing any bundled asset. Sixty-seven times, that adds up.

So port in **two waves**, and the ordering matters:

1. **Wave 1 — the 8–10 most used.** Their purpose is to *prove the kit contract against real
   kits*. Designing the manifest in the abstract and discovering a missing field at kit
   forty is the failure mode this avoids.
2. **Wave 2 — the remainder.** By then it is mechanical, parallelisable, and a genuine
   first contribution for someone outside the team.

Authorship is confirmed: the kits were written in-house, with no contractor or third-party
contribution, so the relicensing path is clean. Still screen each kit for copied snippets as
it is ported — relicensing is irreversible once published, and that check costs minutes per
kit now versus a public retraction later.

### Contribution flow

Add a folder → `pnpm kit:validate` (manifest, purity, schema, examples, licence, a11y) →
open a PR. **No existing file changes.** That is the acceptance test from §2, and for kits
it is enforceable in CI: a PR that touches core to add a kit is a design bug, not a merge
conflict.

First-party kits live in `packages/kits`; their painters register into `packages/react`.
Third-party kits are npm packages resolved from config — see open question 2.

## 11. Adapters, self-hosting and localhost

Vendor coupling exists **only** in `adapters`. The registry wires ports to adapters from
config; no core file names a vendor.

| Port | Adapters (initial set) |
|---|---|
| LLM | Anthropic · OpenAI-compatible (OpenAI, Groq, vLLM, LM Studio) · Ollama |
| Voice | ElevenLabs · OpenAI · Piper (local) · Web Speech (browser, keyless) |
| Image | OpenAI · ComfyUI / Stable Diffusion (local) |
| Moderation | local rules (reference, keyless) · pluggable — **off unless configured** |
| Storage | filesystem (default) · **S3-compatible: AWS S3 · Cloudflare R2 · MinIO · Backblaze B2 · Wasabi** |

### Media storage

A lesson accumulates real weight — generated images, narration audio per line per language,
exported MP4s. Where that lives is a deployment decision, so `MediaStore` is a port like any
other, and the filesystem is only the default that keeps R9 true.

**One S3-compatible adapter covers R2, MinIO, B2, Wasabi and S3 itself** — they speak the
same API, so this is a config difference (endpoint, region, path-style addressing), not five
adapters. Treating R2 as its own integration would be the kind of vendor-shaped code R1
exists to prevent.

What the port must handle regardless of backend:

- **Content-addressed keys.** Media is stored under a hash of its input (§11, TTS caching),
  so the same narration line is never paid for or stored twice, and two lessons can share a
  generated image without either owning it.
- **Presigned URLs, not proxying.** The server hands out a time-limited URL; bytes go
  browser↔bucket directly. Proxying every image through the app is what makes a self-hosted
  install fall over on a class of thirty.
- **A lesson must remain portable.** A document stores media *references*, never a
  bucket-specific URL — otherwise moving from filesystem to R2 breaks every existing lesson,
  and the format stops outliving the tool (§13.1). Resolution to a concrete URL happens at
  render time, through the store.
- **Egress differs sharply between backends.** R2 charges no egress and S3 does; that is
  precisely the kind of trade-off a deployer should be free to make, and precisely why we
  must not assume one.

### The localhost guarantee

**`git clone && pnpm install && pnpm dev` must give a working studio on
`http://localhost:3000` with no account, no API key, and no network call.** This is a tested
guarantee, exercised in CI, not a best effort.

- Default config: filesystem storage, SQLite, Web Speech voice, no moderation. The
  editor and player are fully usable; only generation needs a model.
- Point `LLM_BASE_URL` at Ollama and the whole product runs offline. Local models are a
  security feature — a school can run with no data leaving the building.
- No hardcoded endpoint anywhere. Nothing may assume `bingoo.ai` exists; a deployment must
  work with no account with us, ever.
- **Never require one vendor.** Requiring our key would make this a sales funnel in
  disguise, and the community would say so out loud.
- Ports bind to configurable hosts/ports; nothing assumes a public URL or a fixed origin.

### Handling model output

- **Everything from a model is untrusted input.** Zod at the boundary; whitelist against the
  registry, clamp numbers, drop invented ids.
- **Provenance on every generated artifact:** `{model, promptVersion, contractVersion,
  profileVersions}`. Runs must be auditable and re-runnable.
- TTS is cached on a hash of the **input** `(text, voice, model, locale)`, so the same line
  is never paid for twice, and the routing chain fails over rather than leaving a lesson
  silent.

## 12. Getting this into a teacher's hands

There is a real tension here and it is better named than smoothed over: **"self-hostable
open source" and "usable by someone who has never opened a terminal" pull in opposite
directions.** §11's localhost guarantee serves contributors. It does nothing for a teacher.
The answer is tiered distribution — one product, four front doors.

### Distribution tiers

| Audience | How they get it | What they must understand |
| --- | --- | --- |
| **A teacher, alone** | **Desktop app** — signed installer for macOS / Windows / Linux, bundling the runtime, SQLite and the app | Nothing. Double-click, it opens. |
| **A school or district** | Docker Compose one-liner for their IT person, or the desktop app per machine | Set one API key centrally, once. |
| **A developer** | `git clone && pnpm dev` (§11) | The repo. |
| **Anyone who wants it hosted** | An optional managed instance | An account — **never required** (R8). |

**The desktop app is what decides adoption.** Every other tier serves someone who already
knows what a terminal is. If it slips, the project is open source that only developers can
run, which is a different and much smaller project. It is a phase, not a stretch goal.

### First run — three doors, no YAML

1. **"Try it now"** — no key, no account. Browser voice, sample lessons, editor and player
   fully usable. Generation is *visibly unavailable with an explanation*, never a broken
   button or an error.
2. **"Connect an AI provider"** — pick from a list, paste a key, see it validated live, see
   plainly what it just unlocked.
3. **"Run fully offline"** — detect Ollama/Piper, offer to fetch a model, walk through it.

Rules that make this real rather than aspirational:

- **The Settings UI is the primary configuration surface, not the file.** Both write the
  same resolved shape (§2.4); the UI is the highest-precedence layer, so it always wins for
  the person sitting in front of it. YAML is for IT and contributors, and no teacher is ever
  shown one.
- **No teacher ever types a model ID, an env var or a URL.** They choose from lists built
  from registry descriptors.
- **Key validation is live.** Paste → we call the provider's cheapest endpoint → a green
  tick or a plain-language reason. Never a raw `401`.
- **Errors are written for the person reading them**, in their language, and say what to do
  next: *"Your ElevenLabs credit has run out. Lessons will use the built-in browser voice
  until you top up."* — not `402 Payment Required`.

### Cloud provider mode

The registry (§6) already supports Anthropic, OpenAI, ElevenLabs and the rest. What this
tier adds is the layer above them:

- **A provider picker built from descriptors**, saying what each one unlocks — better
  narration, generated images, faster writing — in outcomes, not in vendor jargon.
- **Cost visibility before and during generation.** An estimate before the run and a running
  total after it. Teachers and bursars fear a surprise bill more than they want a marginally
  better voice, and a tool that hides spend will be banned by the first school that gets one.
- **Deployment-level keys and per-user keys, both.** A school sets one key centrally and
  teachers inherit it; an individual teacher can override with their own. Neither is
  hardcoded as the model.
- **Degradation is the default posture.** A key that expires mid-lesson never blocks the
  work — routing (§2.2) falls down the chain to the keyless path and says so. Compare
  §7: this is the same principle as best-effort stages, applied to infrastructure.
- **Keys are stored server-side or in the OS keychain** — never in the document, never in an
  export, never in a client bundle (R12).

### The parity rule

**Anything a hosted instance can do, a self-hosted install must be able to do with its own
keys.** Hosting may add convenience — backups, sharing, no setup — but never capability.
The moment the open build is the crippled one, the openness is marketing, and the
contributors this architecture is designed to attract will read that immediately and leave.

### A localised interface

The studio UI itself is translated, not only the lessons. Vietnamese teachers are the first
audience and most will not work in English. Note this is a **separate** concern from the
locale packs of §2.1: those carry lesson content and speech metrics, this is application
chrome. Conflating them is a mistake that is expensive to unpick later.

## 13. Embedding this inside another product

The packages are a product too, not just the app. Three depths of integration, and they are
listed in the order we most want them used.

### Depth 1 — the document format, with none of our code

`explainer/v1` is specified in `docs/spec/`. Another system can produce or consume a lesson
with **zero dependency on our packages**, and the exporters (§15) mean an LMS never has to
know we exist. This is the integration that outlives the project, so it is the one the spec
is written to serve. A lesson must never require our runtime to be readable.

### Depth 2 — embed the player

A React component from `@bingoo.ai/explainer-react`, plus a framework-neutral **web
component** wrapper for hosts that are not React — Moodle, Canvas, a PHP site, a Vue app.
The host passes a document, a bundle and a locale; it gets a player.

### Depth 3 — embed authoring or generation

The host supplies storage, auth and media through the existing ports (§6). `apps/server` is
a *reference* implementation of that wiring, never a requirement. A product with its own
database and login should be able to use `generator` and `editor` without adopting our
server at all.

### What embedding demands of the code

This is the part that has to be right from the first commit, because none of it is
retrofittable:

- **No module-level singletons.** The registry is an **instance you construct**, not a
  global. Two lessons with different kit sets must coexist on one page, and a multi-tenant
  host must never leak config between tenants. A global registry is the single easiest way
  to make these packages un-embeddable, and it is free to avoid on day one — so it is a
  **Phase 0 constraint**, not a later cleanup.
- **No side-effectful imports.** `"sideEffects": false`, tree-shakeable, so a host that only
  *plays* lessons never ships the generator or the editor.
- **`react` / `react-dom` are peer dependencies**, never bundled. Two Reacts in one page is a
  support burden we would never escape.
- **Style isolation.** The Stage paints SVG from `RenderModel`, so it carries no global CSS —
  that is an embedding feature, not an accident. Studio chrome must scope its styles and
  must never assume a CSS reset it did not ship.
- **No ambient environment.** No `process.env`, no global fetch interception, no assumed
  origin or base URL (R8). Everything arrives as an argument.
- **A tracked bundle budget for the player path**, enforced in CI. A player that costs two
  megabytes does not get embedded, and nobody discovers this until it is too late to fix
  cheaply.
- **The document format versions separately from the packages**, so a host can pin one
  without the other.

### The first integration is Bingoo itself

The concrete near-term case: Bingoo's private monorepo drops its internal explainer and
depends on these packages instead. That is a useful forcing function — **if Bingoo cannot
adopt it, no outside project can.**

But the direction matters and is easy to get backwards under deadline pressure: **Bingoo
depends on this project; this project never depends on Bingoo.** Nothing here may grow a
Bingoo-shaped assumption to smooth that migration. If the migration needs something, it
gets a generic extension point or it does not get built — that is precisely R8, applied to
ourselves, where it is hardest to obey.

## 14. What we deliberately change from the Bingoo implementation

| # | Bingoo does | Here | Why |
|---|---|---|---|
| 1 | Vendor set, layout templates, quiz kinds, kits, SFX and phase arc are **compiled-in catalogs** | All of it is a **runtime registry** (§2) | This is the difference between a product and an internal tool. Extending must never mean editing core. |
| 2 | Packages export raw `.ts`; the consumer's tsconfig compiles them | Every package builds via `tsup` → ESM + CJS + `.d.ts`, with a real `exports` map | Consumer-compiles-source only works inside one repo. A published package that cannot be imported from a plain Node project is not open source in any useful sense. |
| 3 | No text moderation between WRITE and persist, and no seam for one | A pluggable MODERATE **seam**, shipped wired but off by default | Bingoo leans on APPROVED-only media and code-graded questions, with a human reviewing before publish. A self-hosted tool has no such reviewer, so the hook has to exist — whether a given deployment enables it is theirs to decide. |
| 4 | Vietnamese hardcoded through contract prose, phase names, quiz labels, speech-rate and glyph constants | Locale packs; nothing linguistic in the engine | The single biggest strip job, and what decides whether outside contributors can use the project at all. |
| 5 | Timing/layout constants are literals in `choreographer.ts` / `layout.ts` | Versioned profiles loaded as data, pinned per document | Lets us tune the house style without re-rendering every existing lesson differently. |
| 6 | Quiz types imported concretely from `@bingoo/core` | Pluggable question-kind registry: schema + grader | Genuinely better design — anyone can plug in QTI, H5P or their own item types. |
| 7 | Competency-graph bridge, content bank, auth, Prisma media models | Dropped; `LessonBrief` is the standalone contract | Bingoo's concerns. The brief was already the clean seam. |

Items 1–4 are the ones that would hurt most if deferred, so they are Phase 0/1 obligations,
not cleanup.

## 15. Accessibility and export

- **WCAG 2.2 AA** is a requirement, not a nice-to-have — in education it is frequently a
  legal one. Captions are generated from narration and are part of the document, never an
  afterthought. Contrast is checked in both themes. `prefers-reduced-motion` is respected.
- Exporters are a registry. Initial set, in priority order: **MP4** (headless render),
  **captions (WebVTT/SRT)**, **SCORM 1.2/2004 · xAPI** to feed the LMS people already run,
  and the raw `explainer/v1` document itself.
- The document format is specified in `docs/spec/` and is the property we most want copied.
  A lesson must outlive this tool.

## 16. Phasing

Do not create a package before its phase. If it does not exist yet, it is not that phase yet.

| Phase | Delivers |
|---|---|
| **0** | Repo furniture, CI, licence headers, build/publish pipeline, **config resolver + registry primitives**, `docs/spec` skeleton |
| **1** | `core` + `quality` — document format, profiles, layout, choreographer, `frame`, the three gates, golden tests |
| **2** | `providers` + `adapters` + `react` player + base primitives — a hand-authored document plays; **localhost guarantee green in CI** |
| **3** | `generator` — **brief-building agent + teacher approval** (§8), then brief → structurally validated document via any configured provider; MODERATE seam wired and off |
| **4** | `editor` + `apps/studio` — scene editing, op layer, undo/redo, **settings UI + onboarding wizard + localised interface** (§12) |
| **5** | **Desktop app** — signed installers, bundled runtime, cost visibility (§12) |
| **6** | `kits` — port wave 1 (8–10 kits) to prove the contract, `kit:validate`, contribution docs; wave 2 follows |
| **7** | `apps/cli` + exporters — MP4 (ffmpeg), captions, SCORM/xAPI |

Three notes on the ordering, because it encodes priorities that are easy to drift from:

**Registry and config primitives land in Phase 0** deliberately — they are the hardest thing
to retrofit, since every later package would otherwise be written against static imports.

**Phase 1 is the risky one** and worth over-testing: a pure package with deterministic golden
tests can be locked down hard before anything depends on it.

**The teacher-facing path (4–5) ships before kits and exporters.** If §12 is right that the
desktop app decides adoption, it cannot sit behind two phases of polish. The settings UI is
folded into Phase 4 rather than deferred, because a studio that can only be configured by
editing YAML would need reworking the moment the wizard arrives — and because building the
UI surface alongside the config resolver is what keeps §2.4's precedence chain honest.

## 17. Open questions

Flagged rather than papered over — decide before the phase that needs them:

1. ~~**npm scope.**~~ **Settled: `@bingoo.ai`** — org created, no packages published yet, so
   every name below is free. Packages are prefixed `explainer-*` because the scope is
   org-wide and will host other projects; `@bingoo.ai/core` would be a landmine the first
   time a second project needs a core. Note this is a *different scope* from the internal
   monorepo's `@bingoo/*`, so the two can never collide.
2. **Plugin loading model.** Registries are settled; *how* third-party plugins load is not —
   npm packages resolved from config is the recommendation (no sandbox, no custom loader),
   but it deserves an ADR before Phase 0 ends.
3. ~~**MP4 export path.**~~ **Settled: headless SVG → frames → ffmpeg.** More work than
   Remotion, but Remotion's commercial licence for companies over three people conflicts
   with a wholly Apache-2.0 repo and with R8. The renderer is already pure (§1), so
   rendering frame `t` headlessly is the same call the player makes — the cost is the
   frame pump and encoder plumbing, not new rendering logic. ADR required at Phase 6.
4. ~~**Interactive kits.**~~ **Settled: port Bingoo's 67 kits, relicensed to Apache-2.0,
   in two waves** — see §10. Same company owns them, so the earlier assumption that they
   were off-limits was simply wrong. Kits ship **no bundled assets**; imagery comes from the
   image provider at authoring time. Copyright holder throughout: **Bingoo.ai**.
5. **Desktop packaging (§12) — deliberately deferred, not forgotten.** Tauri vs Electron,
   and the macOS/Windows signing certificates, are decided at Phase 5, not now. Certificates
   cost money and take weeks, and an unsigned installer showing a scary warning would defeat
   the point of §12 — so the lead time is real, but it is lead time on a phase that is
   several phases away, and buying certificates for a product that does not exist yet is
   premature.

   **What Phase 0 must not do is make this choice harder later.** Nothing platform-specific
   in the app, no assumed origin, no reliance on a hosted service — all of which §11 and §13
   already require for other reasons. Revisit at the end of Phase 4, when there is a studio
   worth packaging.
6. **Governance.** DCO sign-off (`git commit -s`) with no CLA is the recommendation: without
   a CLA the project structurally cannot be rug-pulled, which is the strongest trust signal
   available and costs nothing under a single Apache-2.0 licence.
